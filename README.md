## 🔑 このツールが見るもの

署名付きのJWTでも、ペイロードは暗号化されていません。Base64urlを戻すだけで誰でも読めます。署名が正しくても、使えるアルゴリズムや発行者・宛先の確認を欠くと、なりすましにつながる場合があります。RFC 8725は、実際に起きた攻撃と、その対策をまとめたBCPです。

このツールは、トークン1つを手がかりに次を調べます。

- ヘッダーのalgが何で、noneや大文字小文字を変えた書き方になっていないか
- 鍵の場所を指すヘッダー（jku・x5u・jwk・kid）が入っていないか
- 時刻のクレーム（exp・nbf・iat）が、いまの時刻に照らしてどうなっているか
- 発行者と受け手（iss・aud）が入っているか、型は正しいか
- ペイロードに、秘密らしい名前のクレームが入っていないか
- 署名が、自分の持っている鍵で検証できるか。その鍵はRFCが求める長さを満たしているか
- HS256の署名が、用意した候補鍵のどれかと一致するか

作成と署名のタブでは自分でJWTを作り、攻撃の再現タブでは内蔵サンプルを書き換えて、検証側の判断を比較できます。

## ✨ 機能

### デコードと検査

- Base64urlを1文字ずつ検査してデコードする。=が付いている、+と/が混ざっている、文字数が合わないといった誤りを、位置を添えて示す
- ヘッダーとペイロードがJSONオブジェクトであることを確かめ、それぞれの最上位に同じ名前のメンバーが複数あれば指摘する（RFC 7515 §4）
- 検査の結果を危険・注意・情報・良好に分け、RFCの節を添えて並べる
- 時刻のクレームを、UNIX時間・UTC・この端末の時刻・判定の表で示す。時計のずれの猶予は60秒
- 登録済みクレーム（iss・sub・aud・exp・nbf・iat・jti）の意味を並べる
- サンプル4つ（正常・期限切れ・alg=none・危ないヘッダー）

### 署名検証

- HS256・HS384・HS512、RS256・RS384・RS512、PS256・PS384・PS512、ES256・ES384・ES512の12種類
- 検証に使うアルゴリズムは、ヘッダーのalgではなく画面で選ぶ（RFC 8725 §3.1）。食い違えば、その旨を示す
- 鍵は、HSが共有鍵の文字列、それ以外はPEM（SPKI）かJWK。秘密鍵・PKCS#1・証明書・JWK Setは、理由を添えて断る
- 鍵の長さをRFC 7518に照らす（HMACはハッシュの出力以上、RSAは2048ビット以上）
- サンプル5つ（HS256・RS256はPEM・PS256はJWK・ES256はJWK・弱い鍵）

### 作成と署名

- 検証と同じ12種類でJWTを作成。ヘッダーとペイロードをJSONで編集し、algは選んだ方式と一致させる
- HSはUTF-8の共有鍵を入力するか、暗号学的乱数から文字列の鍵を生成する
- RS・PS・ESはページ内で鍵を生成。秘密鍵は取り出せないCryptoKeyとして保持し、公開鍵だけをPEMのSPKI形式で表示する
- ヘッダー・ペイロードの最上位の重複メンバー名と、ヘッダーのcrit・b64=falseを拒否する
- 作成したJWTをコピーするか、デコード・署名検証へ渡せる。検証には共有鍵または公開鍵も渡す

### 弱い鍵の検査

- HS256のトークンを、既定の20候補または改行区切りの候補鍵で検査する
- 上限は1000件、候補1個につきUTF-8で1024バイト、候補欄全体で1048576文字（UTF-16コード単位）
- 空行を無視し、鍵の先頭・末尾の空白は保持する。進捗を表示し、途中で中止できる
- 一致した候補鍵と検査件数を表示する。未発見は鍵の安全性を示すものではない

### 攻撃の再現

- 内蔵のRS256サンプルで、alg=noneによる署名省略と、RS256からHS256への取り違えを再現する
- ペイロードのroleをadminへ変更し、脆弱な実装とRS256に固定した実装の受理・拒否を並べる
- 元のJWT、変更後のJWT、公開鍵を表示する。外部のトークンやURLを攻撃先として指定する機能はない

### 学習

- 構造、ペイロードが読めること、alg=noneとアルゴリズムの固定、鍵の強さ、鍵を指すヘッダー、時刻と相手の検証を、RFCの節を添えてまとめる

### 共通

- 日本語と英語の切り替え（`?lang=ja`・`?lang=en`、選んだ言語を保存）
- ライト・ダークの切り替え（保存した選択がなければOSの設定に従う）
- キーボード操作（タブは矢印キー・Home・Endで移動）
- 「全入力と鍵を消す」で全タブの入力・結果・保持している鍵を破棄。クリップボードは対象外
- 入力・例・方式の変更やクリアで古い非同期結果を破棄し、言語変更時は現在の結果も翻訳し直す

## 📖 使い方

### デコードと署名検証

1. 「デコードと検査」タブにJWTを貼り付けます。サンプルのボタンでも試せます。
2. 検査の結果を上から読みます。危険・注意には、RFCのどの節に照らした指摘かが書いてあります。
3. 署名を確かめるときは「署名検証」タブへ移り、アルゴリズムを選んで鍵を貼り付けます。トークンはデコードのタブと同じ欄を使います。
4. 「ヘッダーのalgに合わせる」を押すと、ヘッダーのalgに切り替わります。わざと違うものを選んで、通らないことを確かめられます。

### JWTの作成

1. 「作成と署名」タブで「JSON例を入れる」を押し、方式にES256を選びます。
2. 「鍵を生成」を押して、公開鍵が表示されるのを待ちます。秘密鍵は表示・保存されません。
3. 必要に応じてペイロードを編集し、「JWTを作成する」を押します。
4. 「署名検証へ渡す」を押すと、JWT・ES256の選択・公開鍵が署名検証の画面へ渡ります。「署名を検証する」を押して結果を確かめます。

HSを使う場合は共有鍵を入力するか生成します。「JSON例を入れる」は現在の方式と鍵を保持し、JSONだけを例に置き換えます。方式を変更すると鍵を破棄するので、新しい方式で生成し直してください。

### 小辞書による検査

1. 「弱い鍵の検査」タブで「弱い鍵の例を入れる」を押します。
2. 「検査する」を押すと、既定の20候補から一致する鍵が見つかります。
3. 自分のトークン、または許可を得たトークンを検査するときは、JWTと候補欄を入れ替えます。「デコードの入力を使う」でもJWTを渡せます。
4. 中止するときは「中止」を押します。候補が見つからなかった場合も、安全性を証明したことにはなりません。

### アルゴリズムの取り違えの再現

1. 「攻撃の再現」タブで、alg=noneまたはRS256→HS256のシナリオを選びます。
2. 「再現する」を押し、変更後のJWTを脆弱な実装だけが受理することを比較表で確かめます。
3. 元のJWTと変更後のJWT、変更理由を読みます。「署名検証へ渡す」ではRS256と公開鍵を渡すので、選択を変えずに署名を検証できます。

使い終わったら「全入力と鍵を消す」を押してください。クリア後に例や鍵を自動で戻すことはありません。

## 🔬 技術的な説明

### JWTの構造

JWS Compact Serialization（RFC 7515 §7.1）は、ヘッダー・ペイロード・署名をそれぞれBase64urlにして、ドットでつないだ形です。Base64urlは末尾の=を付けません（§2）。署名は「ヘッダー.ペイロード」の文字列全体にかかるため、1文字でも変えると署名は合いません。

### 検査の項目

| 項目 | 判定 | 根拠 |
|---|---|---|
| alg=none | 危険 | RFC 8725 §2.1。署名がないので中身を誰でも書き換えられる |
| algがNone・NONEなど | 危険 | RFC 7515 §4.1.1はalgを大文字と小文字を区別する文字列と定める。区別せず比べる実装ではnoneになる |
| jku・x5u | 危険 | RFC 8725 §3.10。検証側が取りに行くと、攻撃者の指すサーバーへ要求を送らされる |
| jwk | 危険 | トークン自身が公開鍵を運ぶ。この鍵で検証すると誰でも署名を作れる |
| kid | 注意 | RFC 8725 §3.10。鍵の選択にそのまま使うとインジェクションの入口になる |
| crit | 注意 | RFC 7515 §4.1.11。理解できない拡張が挙がっていれば拒まなければならない |
| 同じ名前のメンバーの重複 | 危険 | RFC 7515 §4。実装によってどちらを読むかが変わる |
| expが現在時刻以前 | 危険 | RFC 7519 §4.1.4。expと同じ秒も期限切れとして扱う |
| nbfが未来 | 危険 | RFC 7519 §4.1.5 |
| iatが未来 | 注意 | RFC 7519 §4.1.6 |
| iss・audがない | 注意 | RFC 8725 §3.8・§3.9 |
| typがない | 情報 | RFC 8725 §3.11は種類の明示を勧める |
| 秘密らしい名前のクレーム | 危険 | ペイロードは署名されているだけで暗号化されていない |

### 対応するアルゴリズム

| 族 | 名前 | Web Cryptoでの名前 | 検証用の鍵 |
|---|---|---|---|
| HS | HS256・HS384・HS512 | HMAC | 共有鍵（UTF-8の文字列） |
| RS | RS256・RS384・RS512 | RSASSA-PKCS1-v1_5 | 公開鍵（PEMのSPKIかJWK） |
| PS | PS256・PS384・PS512 | RSA-PSS | 公開鍵（同上） |
| ES | ES256・ES384・ES512 | ECDSA（P-256・P-384・P-521） | 公開鍵（同上） |

PSの塩の長さはハッシュの出力と同じにします（RFC 7518 §3.5）。ESの曲線はアルゴリズムで決まります（§3.4）。

作成ではHSに共有鍵を使い、RS・PS・ESにはページ内で生成した秘密鍵を使います。RSAの生成鍵は2048ビットです。秘密鍵は`extractable:false`で生成し、同じページで生成した鍵を、生成時と同じアルゴリズムで使う場合だけ受け付けます。公開鍵はPEMのSPKIとして出力し、署名検証へ渡せます。

### HSの鍵生成と文字列

HSの鍵を生成するときは、Web Cryptoの`getRandomValues`でハッシュ出力と同じビット数の乱数を取り、Base64urlの文字列へ変換します。その文字列をデコードせず、UTF-8の共有鍵として使います。

| アルゴリズム | 生成する乱数（バイト） | UTF-8の鍵文字列（文字＝バイト） |
|---|---|---|
| HS256 | 32 | 43 |
| HS384 | 48 | 64 |
| HS512 | 64 | 86 |

検証画面に表示するHSの鍵の大きさは、UTF-8のバイト数を8倍したビット数です。Base64urlへ変換して文字数が増えても、元の乱数よりエントロピーが増えるわけではありません。

### 鍵の長さ

RFC 7518 §3.2は、HMACの鍵をハッシュの出力以上の長さにすることを求めています（HS256なら256ビット）。RSAは2048ビット以上です（§3.3・§3.5）。RFC 8725 §3.5は、人が覚えられるパスワードをHS256の鍵に直接使ってはならないとしています。推測しやすい鍵は、手元で候補を試す辞書攻撃で見つかることがあります。長さだけで推測の難しさを判断することはできません。

このツールは、検証が通った場合でも、鍵が短ければ危険として示します。

### アルゴリズムの固定

RFC 8725 §3.1は、検証側が使えるアルゴリズムを呼び出し側に決めさせ、それ以外を使わないことを求めています。許可する方式や鍵の種類を制限せず、ヘッダーのalgに従う実装では、次のような攻撃が成立する場合があります。

- algをnoneに書き換えたトークン
- RS256をHS256に書き換え、公開鍵をHMACの共有鍵として署名し直したトークン（CVE-2015-9235）

署名検証タブの`JwtVerify.verify`は、画面で選んだアルゴリズムで署名を確かめ、ヘッダーとの違いを別に示します。返す`valid`は署名の一致を表し、認証・認可の判定ではありません。

攻撃の再現タブでは、内蔵のRS256サンプルだけを使います。noneの例では署名を省略し、取り違えの例では公開PEMの文字列をHMACの共有鍵として使います。安全側の比較対象はRS256に固定し、ヘッダーのalgがRS256と一致しなければ署名検証の前に拒みます。いずれもroleをadminへ変え、元のサンプルと変更後を並べます。認証・認可には、発行者・宛先・有効期限や、アプリケーションの権限の検証が別に必要です。

## 🎯 ユースケース

- 自分のサービスの点検：発行しているトークンのexp・iss・aud・鍵の長さを確かめ、許可された範囲でHS256の候補鍵を検査する
- 実装のレビュー：alg=noneやアルゴリズムの固定を、動く画面で示して共有する
- CTF・演習：配られたトークンをデコードし、候補鍵を検査して、自分で署名したトークンと比べる
- 教育：JWTが暗号化されていないこと、署名が何を守るのかを、ペイロードを読ませて理解させる
- 設計の検討：HS・RS・PS・ESの違いと、鍵の配り方の違いを並べて比べる
- 研究・実装比較：署名の一致とアルゴリズムの受理条件を分けて調べ、内蔵サンプルの結果を説明に使う
- デバッグ：認証が通らないとき、期限切れなのか、鍵が違うのか、アルゴリズムの選択が違うのかを切り分ける
- 資料づくり：検査の結果の画面を、社内のガイドラインやレビューの基準に添える
- 授業・研修：鍵生成・署名・検証を行い、alg=noneと公開鍵の取り違えを内蔵サンプルで確かめる

## 🔒 セキュリティ

- Content Security Policy（metaタグ）：`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`。インラインのスクリプト・スタイルを許さず、外部への通信もしない
- トークンも鍵も、ブラウザーの中だけで処理し、外部へ送らない。アプリケーションの保存領域へ書き込まない
- トークンと鍵の入力欄は、スペルチェックと自動補正を切っている（入力した鍵が外部のスペルチェックに送られないようにするため）
- 画面の組み立てはDOM（`textContent`）で行い、`innerHTML`を使わない
- `<meta name="referrer" content="no-referrer">`、外部リンクは`rel="noopener noreferrer"`
- ブラウザーに保存するのは、言語とテーマの選択だけ
- 鍵生成・署名作成・署名検証はWeb Cryptoで行い、外部のライブラリーを使わない
- 非対称の秘密鍵はメモリー内の取り出せないCryptoKeyとして扱い、秘密鍵の入力・ファイル保存・書き出しを提供しない
- 辞書検査は件数と入力サイズを制限し、処理の合間に画面操作を受け付ける。入力変更後やクリア後に完了した古い結果は表示しない

## ⚠️ 注意と限界

- サンプルの鍵は、このツールのデモ用に作ったものである。本番の鍵ではない
- 本番の鍵やトークンを扱うときは、自分の端末で開き、使い終わったら入力欄を消す
- 小辞書チェックは自分のトークン、または検査の許可を得たトークンに使う。HS256のみで、上限は1000件、候補1個につきUTF-8で1024バイト、候補欄全体で1048576文字（UTF-16コード単位）
- 候補が見つからない結果は、その候補一覧で署名が一致しなかったことだけを示す。鍵の安全性や推測困難性の証明にはならない
- 生成した非対称の秘密鍵はページのメモリー内だけにあり、クリア・方式変更・ページの再読み込みで失われる。外部の秘密鍵の読み込みや生成秘密鍵の書き出しはできない
- 「全入力と鍵を消す」は表示・結果・保持参照を破棄するが、ブラウザーのメモリーをゼロで上書きする保証はない。Web Cryptoで実行中の処理そのものは止めず、古い完了結果を破棄する
- コピー済みのクリップボードはクリアの対象外。各タブのクリアはそのタブだけに作用するため、転送先も消すときは「全入力と鍵を消す」を使う
- EdDSAと、JWE（暗号化されたJWT）には対応していない
- JWK Setの読み込みと、jkuのURLからの鍵の取得はしない（外部への通信をしない方針のため）
- 検査は、トークン1つからわかることに限られる。署名の一致だけでは認証・認可は完了しない。発行者・宛先・有効期限・権限は検証側のアプリケーションが確認する
- 重複メンバー名の検出はヘッダーとペイロードの最上位だけ。入れ子のオブジェクト全体を検査する機能ではない。作成では最上位の重複と、ヘッダーのcrit・b64=falseを拒む
- トークンは16384文字までを読む
